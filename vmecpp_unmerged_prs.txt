=== PR #511 [OPEN, draft] Imbalance-aware radial partitioning ===

--- description by jurasic-pf, 2026-05-04 18:26 UTC ---
Boundary threads (0, N-1) have an additional constant per-call overhead beyond the usual per-surface cost:
* degenerate-axis init at j=0
* NESTOR/free-boundary handover at j=ns-1, etc.

Under equal-share partitioning these threads consistently arrive last at every team barrier, and the gap grows with thread count. The result is a scaling cliff: 8-30% of thread-time is wasted at barriers waiting for the boundary threads, and adding more threads yields diminishing returns past ~10 threads.

Reframe the partition as distributing `total_work = num_surfaces + k_axis + k_lcfs` *effective work units* evenly across threads, then convert each thread's assigned work back to a surface count by subtracting the inherent boundary overhead it carries (k_axis surfaces of axis overhead for tid 0, k_lcfs for tid N-1). With Hamilton's method to distribute the integer remainder, the resulting partition is makespan-optimal under the contiguous-slice constraint:

  * At low thread counts the boundary overhead is a small fraction of
    total work, so the partition converges to the equal partition.
  * At high thread counts it shifts a meaningful number of surfaces
    off the boundaries onto the interior, balancing per-thread work.

Both `k_axis` and `k_lcfs` live in `vmec_algorithm_constants.h` as `kBoundarySurfacesOffAxis` (=2) and `kBoundarySurfacesOffLcfs` (=1). They were derived empirically by sweeping wall-clock time across
(NS, num_threads); see VMECPP_AXIS_SURFACES_OFF and VMECPP_LCFS_SURFACES_OFF env vars for runtime override.

## Problem

`lbsubs` was listed as unimplemented in the README, and `ComputeOutputQuantities` left the full-grid covariant `B_s` as the linear half-to-full interpolation of the metric-element `B_s`, with a standing `TODO` at the call site (`re-compute B_s to solve radial force balance (lbsubs flag in Fortran VMEC)`). The `jxbout` diagnostic that consumes the `B_s` tangential derivatives — `itheta`/`izeta` (the `sqrt(g)` `K^{u,v}` currents) and `bsubs3` — therefore omits the current-sheet correction that the `lbsubs` path captures.

## Change

Add a `VmecINDATA::lbsubs` flag (parsed from JSON, persisted to/from HDF5, round-tripped through `ToJson`; default `false`) and implement `RecomputeBSubSFromRadialForceBalance`, a port of the `IF (lbsubs)` branch of `jxbforce.f90` together with the collocation solve in `getbsubs.f90`. On each interior full-grid surface it solves

[code omitted]

in spectral space, where `brho` is the `sqrt(g)`-weighted radial-force residual with the flux-surface-averaged force balance subtracted (the local equation is otherwise unsolvable, since that surface integral vanishes identically). The recovered coefficients overwrite the interior `bsubs_full` and its tangential derivatives `bsubsu`/`bsubsv`; axis and edge are filled by the existing `ExtrapolateBSubS`. The solve is guarded: a singular matrix or a residual above `1e-8 * |rhs|` logs a warning and leaves that surface at its half-to-full interpolation. === PR #561 [OPEN] CUDA port of the iteration body (opt-in via VMECPP_USE_CUDA) ===

--- description by CharlesCNorton, 2026-06-10 22:11 UTC ---
# CUDA port of the iteration body (opt-in via VMECPP_USE_CUDA)

## Summary

This PR adds an opt-in CUDA execution path for the iteration body,
covering fixed-boundary and free-boundary configurations. Built with `-DVMECPP_USE_CUDA=ON`, the per-iteration chain (forward
toroidal transform, Jacobian and metric elements, MHD forces, inverse
transform, preconditioning, residuals, time step) executes on the GPU with
device-resident state; `vmecpp.run` and `vmec_standalone` use it
transparently for supported inputs. A batched mode solves N equilibria
concurrently inside one CUDA context, exposed to Python as
`run_batched_gpu`: a broadcast call returns the single converged result of
the seed configuration, and a distinct call returns one `OutputQuantities`
per configuration, derived directly from the batched run's flushed device
state; each carries that configuration's own iteration count and final
force residuals, snapshotted while it was still active so a converged
configuration reports its own residual rather than a post-mask zero. Every
environment variable the binding sets is restored when the call returns.

The option defaults to OFF. Without it, the build requires no CUDA toolkit
and contains no CUDA reference.

The build runs on Linux and natively on Windows with the MSVC host
compiler (system dependencies from vcpkg, the Ninja generator, and a
CUDA compiler launcher that adapts the MSVC command line). All
Windows-specific handling is guarded under `_WIN32`/`MSVC`, so the Linux
build is byte-identical; the native Windows module builds and runs `cma`
on an RTX 6000 Ada to the canonical result. See the Windows section of
the docs for the exact steps.

Documentation: `docs/cuda_acceleration.md` (scope, build, correctness
contract, batched mode, and a reference of every runtime control).
Regression coverage: `tests/test_cuda_gpu.py`, opt-in via
`VMECPP_TEST_CUDA=1` since it requires a CUDA build and a GPU.

## Scope

Supported: fixed-boundary and free-boundary, stellarator-symmetric
(`lasym = false`) configurations, both axisymmetric (`ntor = 0`, the
degenerate `nZeta = 1` case) and three-dimensional (`ntor >= 1`), on a
single radial rank, in both the single and the batched execution modes.
Free-boundary runs keep the NESTOR vacuum solve on the host with
per-iteration bridges to the device-resident iteration state; the
segment and whole-iteration CUDA graphs are disabled for them, since
the edge-force kernel toggles with the vacuum pressure state. Sync
elision covers free-boundary runs: iterations run live until the
vacuum contribution is fully active, then the scalar sync sites elide
while the vacuum block keeps its per-iteration cadence (the NESTOR
response must track the boundary every iteration; a boundary-cadence
vacuum solve was measured non-convergent and rejected). Batched free-boundary runs carry one NESTOR
instance per configuration against one loaded mgrid (every input in the
batch must share `mgrid_file` and `extcur`; boundaries and plasma
profiles may differ in distinct mode); the vacuum activation, the
`nvacskip` cadence, and the soft-start restart are batch-wide decisions,
and the per-iteration vacuum solves serialize on the host across the
configurations, which bounds the batched free-boundary speedup below
the fixed-boundary one.

Enforced at runtime under the CUDA build:

- `Vmec::run` rejects `lasym = true` inputs with
  `absl::UnimplementedError` before any iteration work, along with batched
  free-boundary inputs whose vacuum solver is not NESTOR.
- Inputs with `nThetaReduced > 256` are rejected with
  `absl::UnimplementedError` (a poloidal-scatter kernel-layout limit). The
  radial resolution is accepted up to `CudaMaxRadialResolution()`: the
  parallel cyclic reduction solver carries one thread per radial row through
  1024 rows, and the block-Thomas solver holds its elimination ratios in
  dynamic shared memory sized to `ns` above that, so the device's opt-in
  shared-memory capacity sets the ceiling; an `ns` beyond it is rejected.
- An estimate of the run's device-memory footprint is checked against the
  device's free memory before the first allocation; an oversized batch is
  rejected with `absl::ResourceExhaustedError` instead of failing at an
  allocation deep inside the iteration body.
- CUDA and cuFFT failures surface as recoverable error statuses (a Python
  `RuntimeError` through the bindings) instead of terminating the process;
  the next run re-stages the device state from scratch.
- The radial domain is not partitioned across OpenMP threads;
  `num_threads` is clamped to 1 (host threading offers no benefit when the
  iteration body runs on the device).

## Changes when the option is OFF

The CPU algorithm and its behavior are unchanged. Two things in shared
code are new:

1. `FlowControl` gains per-configuration state vectors (sized 1 and inert
   outside the batched CUDA mode) and a typed `RestartReason` enum with
   documentation of the Fortran `irst` correspondence.
2. `ideal_mhd_model.cc` gains phase-timing instrumentation
   (`phase_timer.h`): an RAII scope timer around each iteration phase that
   writes a summary to a file under `/tmp` (path configurable via
   `VMECPP_PHASE_TIMING_PATH`). The instrumentation is compiled only under
   `VMECPP_USE_CUDA`; in CPU-only builds the macro expands to nothing.

The remaining CPU-side changes are `#ifdef VMECPP_USE_CUDA` dispatch
sites and are compiled out.

## Architecture

- All iteration state (spectral coefficients, geometry, forces,
  preconditioner matrices, velocity and position of the time integrator)
  persists in device buffers across iterations. Host transfers are limited
  to a small number of scalars per iteration (Jacobian tau extrema,
  residual triples, plasma volume), plus consolidated flushes at
  preconditioner-update and end-of-run boundaries.
- The toroidal transforms run as batched cuFFT plans; the poloidal
  transforms are fused into fill/scatter kernels on either side. The
  dealias and scatter kernels warp-pack `32 / nThetaReduced` zeta planes
  onto each 32-lane warp (default on), filling the lanes the one-plane
  layout left idle when the reduced poloidal extent is 16.
- Three sync-free segments of the iteration body are captured as CUDA
  graphs and replayed per iteration (default on, each individually
  defeatable by environment variable).
- The batched mode sizes every per-configuration buffer by
  `VMECPP_N_CONFIG_MAX` and carries a configuration axis on each kernel
  grid. Per-configuration residual evolution, convergence gating,
  time-step control, bad-Jacobian restart, and an active-configuration
  kernel mask let configurations converge independently; a configuration
  that exceeds its iteration cap is marked timed out without failing the
  batch.

## Correctness

Contract, verified on fixed-boundary stellarator configurations through
the full multigrid ramp:

- `aspect_ratio` matches the CPU result bit for bit.
- Volume-averaged and field-line-derived output quantities match within
  1e-5 to 1e-3 relative. The origin is floating-point summation-order
  differences in reductions; each such reduction is documented at its
  kernel.
- Iteration counts, restart-reason sequences, and multigrid stage
  transitions match the CPU trajectory. On inputs that trigger mid-run
  bad-Jacobian restarts, the timing of restart events is sensitive to
  the documented drift, so iteration counts there match approximately
  rather than exactly (W7-X converges in 3146 iterations against the
  CPU's 2954, to the same equilibrium).
- On free-boundary runs the boundary itself responds to the vacuum
  field through the drift-sensitive trajectory, so every converged
  output carries the drift family there; the bit-exact `aspect_ratio`
  clause applies to fixed-boundary runs.

Reductions that feed the time-step controller and the convergence gate use
serial or order-preserving device implementations and match the CPU bit
for bit per call. Reductions covered by the drift tolerance (for example
the differential volume under the fused atomicAdd kernel) are documented
as such.

## Runtime controls

`docs/cuda_acceleration.md` documents every environment variable. Three
classes:

1. Production-path switches, default ON, each falling back to a slower
   equivalent path (kernel fusions, the dealias and scatter warp-packs,
   pair-coarsened variants, parallel residual reduction, the three CUDA
   graphs, the device-side convergence gate, the per-configuration
   time-step controller). These exist so a
   misbehavior on untested hardware can be bisected per subsystem.
2. Opt-in throughput modes, default OFF (K-window sync elision,
   deferred-sync residuals, a whole-iteration CUDA graph under elision).
3. A mixed-precision and alternate-FFT experiments annex, default OFF,
   with measured outcomes recorded per gate (FP32/TF32 scatter variants
   with double-single compensation, Ozaki-slice multiplications on FP32
   and on int8 tensor cores with exact integer accumulation, a
   Carson-Higham iterative refinement on the RZ tridiagonal solve,
   hand-coded radix-8x3 DFTs). None of these are on the production path.
   They are included because the negative results are documented in code
   and prevent re-exploration; if you prefer the annex out of this PR, I
   will split it into a follow-up.

`VMECPP_CUDA_DEVICE` selects the device ordinal for the process
(default 0; multi-GPU batches run one process per device). The
run-scoped controls (`VMECPP_N_CONFIG_MAX`, `VMECPP_SYNC_ELIDE`,
`VMECPP_PER_CFG_NITER_CAP`, and the batch upscale gates) are re-read at
the start of every run, so successive runs in one process can carry
different settings.

## Known limitations

- The `<M>` (volume-averaged spectral width) column and the `specw`
  output evaluate the current iteration state under the CUDA build; the
  CPU path evaluates the restart backup, which lags by one iteration, so
  the printed column can differ in the trailing digit at a given
  iteration.
- In distinct mode the per-configuration `OutputQuantities` derivation
  is the default (`VMECPP_PER_CFG_RECOMPUTE=0` opts out, falling back to
  a hot-restart reconstruction per configuration); the subprocess
  recompute (`recompute_outputs_from_spectra`) and the raw converged
  spectra (`return_spectra=True`) remain available.

=== PR #637 [OPEN, draft] free_boundary: BIEST solver, dual-run diagnostics, standalone harness ===

--- description by jurasic-pf, 2026-07-11 17:41 UTC ---
Adds **BIEST as a user-selectable free-boundary solver** (`free_boundary_method = "biest"`), plus the diagnostic tooling used to validate it.

## BIEST solver
Solves the same exterior Neumann problem as NESTOR (`B_vac · n = 0`, prescribed net toroidal current) with high-order partition-of-unity singular quadrature + GMRES, replacing NESTOR's low-order singularity subtraction + dense LU. New input `biest_accuracy_digits` (default 8, range [1,14]) plumbed through JSON/HDF5/pybind/pydantic.

Design notes:
- coil `B·n` computed with BIEST's own normals (`ComputeBdotN`) — the normal-orientation convention stays internal to BIEST; net current enters as `Jplasma = signgs·μ0·I_tor`.
- **full solve on the fresh boundary every update.** Frozen-field or frozen-operator schemes were measured to stall or slow VMEC's descent (dual-run diagnostics below); per-iteration fresh solves converge in *fewer* iterations than NESTOR (421 vs 489 on CTH-like) with ~25 % lower converged DELBSQ. Experimental partial updates remain behind `VMECPP_BIEST_PARTIAL_DRIFT_TOL`.
- thread-cooperative: partition deposit → pinned-thread solve → partition readout. The solve must run on the *same* thread every update (solver state persists) — an `omp single` is not sufficient.

## Validation (cth_like_free_bdy, mpol=5, nzeta=36, 43 kA)
| check | result |
|---|---|
| bsqvac NESTOR vs BIEST | 0.83 % rel RMS — equals NESTOR's discretization floor |
| BIEST self-convergence (digits 8 vs 12) | 2e-9 RMS |
| I_tor from solution | 43228.9 A (input 43229.08; NESTOR: 43227.1) |
| in-loop | ftol 1e-10 in 421 iterations |

## Diagnostics
- `DualSolver`: run any solver with the other as a shadow (`VMECPP_FB_SHADOW`, `VMECPP_FB_DUAL_DUMP`); one JSONL record per vacuum update with both |B|²/2 fields + boundary coefficients.
- `tools/plot_fb_dual_run.py`: side-by-side imshow (primary | shadow | diff), poloidal-spectrum evolution across the iteration, scalar traces.
- `vmecpp_tools/free_boundary_standalone`: A/B harness evaluating any solver at a fixed boundary.
- `docs/free_boundary_solvers.md`.

Known cost: BIEST runs serially inside the OpenMP parallel region (~2.8 s per solve at digits 8 on CTH) — it is the accuracy reference; use Vac2 (next PR) for fast accurate production runs.

Part 2/4, stacked on https://github.com/proximafusion/vmecpp/pull/636.

=== PR #638 [OPEN, draft] free_boundary: Vac2 (Strumberger) solver with stellarator-symmetry fold ===

--- description by jurasic-pf, 2026-07-11 17:41 UTC ---
Adds **Vac2 (Strumberger/Tichmann) as a third free-boundary solver** (`free_boundary_method = "vac2"`), a C++ port of the Strumberger/Tichmann vac2 Fortran solver (formulation context: Merkel & Strumberger, arXiv:1508.04911).

Vac2 solves the same exterior Neumann problem as NESTOR with a reformulated kernel that avoids the factorial growth of NESTOR's analytic `c_mn` coefficients: accuracy improves monotonically with resolution instead of saturating at mpol ≈ 12–16.

## Why this matters
On cth_like_free_bdy at **production resolution**, Vac2's vacuum pressure agrees with BIEST (the accuracy reference) to **2.0e-3 rel RMS vs NESTOR's 8.3e-3**, and improves to 7.3e-4 at ntheta=64 while NESTOR stays pinned at its formulation floor. In-loop it converges in 420 iterations (NESTOR: 489) to the accurate DELBSQ floor (9.4e-4 vs NESTOR's 1.23e-3) — i.e. **BIEST-class accuracy at near-NESTOR cost**.

## Performance (best-of-3, CTH-like full run)
| configuration | wall |
|---|---|
| Vac2 (this PR) | 2.4 s |
| NESTOR, full updates every iteration | 0.58 s |
| NESTOR production (frozen-matrix partials) | 0.33 s |

Levers implemented:
- **stellarator-symmetry column fold** in the kernel assembly: the mirrored column's row-FFT is the complex conjugate of the canonical one, so its mode arrays are exact sign-flipped copies — verified to 5e-16 against the unfolded path (`VAC2_NO_SYMM_FOLD=1` kill switch). Halves the dominant O(nuv²) work.
- bounded nested OpenMP team for the solve inside VMEC's parallel region (otherwise it runs serial on the pinned thread); `VMECPP_VAC2_SOLVE_THREADS` override.
- NESTOR-style frozen-operator partial updates (cached Cholesky factor + fresh RHS) implemented but **opt-in** (`VMECPP_VAC2_PARTIAL_UPDATES=1`): identical converged answer but ~2.6× iterations — the same frozen-operator descent pathology observed with BIEST partials.
- the FFT path uses the FFTW3 API via Intel MKL's FFTW interface (FFTW itself is GPL).

## Wrapper conventions (following the Fortran vac2 reference)
Full poloidal grid, u,v ∈ [0,1); surface-area-weighted normal `signgs·(Xu×Xv)` (**not** normalized — normalizing produced a smooth 9 % bsqvac error with perfect current integrals); `bexn = +(B_coil·n)` with the coil field only — net current via the secular term `curtor = μ0·I_tor`; `curpol = ⟨xv·B⟩`.

Limitations: `lasym` not yet supported by the wrapper; `nzeta == 1` unverified (NESTOR covers axisymmetric); known follow-ups: stage-3 symmetry fold, FFTW plan caching.

Part 3/4, stacked on https://github.com/proximafusion/vmecpp/pull/637.

=== PR #769 [OPEN] Add opt-in Anderson acceleration of the descent iteration ===

--- description by CharlesCNorton, 2026-09-01 17:53 UTC ---
**Change** - `VmecInput.anderson_acceleration`, off by default, switches on Anderson acceleration of the descent iteration (JSON and HDF5 round trip through `VmecINDATA`); `Vmec::SetAndersonAcceleration(window, start_iteration, frequency, zero_velocity_on_jump)` keeps the tuning parameters for C++ callers. One Garabedian time step maps the Fourier state x to g(x). `AndersonAcceleration` keeps a short per-thread history of map outputs and residuals r = g - x; the team solves the least-squares problem for the combination of recent residual differences that best cancels the current residual, each thread applies that combination to its map outputs, and the momentum restarts. A thread stores the history of its own slice over its full stored radial range, satellite points included, so the combination stays consistent at the partition seams. The k x k normal equations are the only cross-thread data: `SumInFixedTree` reduces them over a binary tree fixed by thread id, they are Tikhonov-regularized by 1e-12 of their mean diagonal, and a combination that is not finite or exceeds 100 in magnitude is skipped. The defaults are a window of 2, engagement 25 iterations after a stage starts or restarts, and disengagement once fsqr + fsqz + fsql falls below max(1e-4, 1e-3 x the residual at stage entry, 1e3 ftol). Free-boundary runs are included.

**Cause** - the extrapolation pays in the nonlinear phase at the start of each multigrid stage, where the descent is still finding the basin. In the tail the fixed-point map is linear and the momentum iteration already converges at its optimal rate; extrapolating there held the residual in a limit cycle on the QUASR fixed-boundary cases at ftol 1e-9, so the tail is handed back to the descent. An earlier study ran Anderson from fsq = 1e-6 down, where it loses.

=== PR #772 [OPEN] Carry the sign of the Jacobian in chi ===

--- description by CharlesCNorton, 2026-09-02 12:49 UTC ---
**Change** - `chi` carries the sign of the Jacobian: `ComputeIntermediateThreed1FirstTableQuantities` forms it as `2 pi * sign_of_jacobian * chi1`, and `wout.chi` follows.

**Cause** - `chi` was accumulated as `2 pi * chi1` with `chi1 = sum(phipH * iotaH) * deltaS`, while `phi`, `phipf` and `chipf` all carry `sign_of_jacobian`. With the usual negative Jacobian the wout therefore held `chi` = minus the integral of iota over phi. Fortran VMEC has the same omission (`eqfor.f`, `chi = twopi*chi1`) and PARVMEC 10.0 reproduces it, so the reference wout files hold the negated profile.

=== PR #878 [OPEN] Shorten time steps that would make flux surfaces cross ===

--- description by CharlesCNorton, 2026-09-22 19:06 UTC ---
## Change

`jacobian_safe_step` (default false) shortens every time step at whose end the half-grid Jacobian `tau` would fall below 1% of its value at the start of the step, at some grid point.

After each step, the evaluation compares `tau` with its value at the start of the step. `tau` is a quadratic form in the geometry, so along the step it is exactly quadratic in the step length. Where `tau` has fallen below the bound, this gives the largest fraction of the step that keeps it. The state then moves back along the step to that fraction, the velocity is scaled by the same fraction, and the model is evaluated again. A backup taken at the end of the step moves to its start, the last evaluated state.

Steps that keep the bound are unchanged, and so is the iteration with the flag off. The C++ solve and the Python iteration of `solve_equilibrium` take the same steps. The iterations reached by a shortened step are listed as `RestartReason.SHORTENED_STEP` in `wout.restart_reasons`.

## Cause

On main, a step that makes the Jacobian change sign is detected only after it is taken. The step is undone to the last backup and retried with a time step 10% smaller. After 75 of those, the run fails with `JACOBIAN_75_TIMES_BAD`. The time-step control of VMEC 8.52 counts a 100-fold growth of the residual towards the same 75, so the error also ends runs in which no surface crossed.

## Evidence

The test set is 3000 random boundaries of the ConStellaration training set, 1003, 987 and 1010 from its three shards, run with the VMEC++ inputs of the ConStellaration forward model's low-fidelity preset: ns = 25, then 71, at time step 0.7. On main, 163 of them fail:

| failure on main | count | with `jacobian_safe_step` |
|---|---|---|
| `JACOBIAN_75_TIMES_BAD` | 24 | 12 converge, 9 fail the same way, 3 reach the iteration limit |
| iteration limit | 80 | 80 fail |
| in the first iterations | 59 | 59 fail |

The flag converges 9 of the 11 `JACOBIAN_75_TIMES_BAD` failures from shard 0, 3 of 3 from shard 1 and none of the 10 from shard 2. The Python iteration classifies the restarts of main's 24: 16 restart on surface crossings alone, 2 on residual growth alone and 6 on both. With the flag no step crosses surfaces, and the 12 runs that still fail restart on residual growth and slow progress.

The 12 converging runs shorten 1 to 9 steps (median 3.5), all within the first 50 iterations of a multigrid stage, and keep a median 76% of a shortened step. Main at time step 0.5 converges 13 of the 24; where both converge, the flag at 0.7 takes a median 0.98 of the iterations of main at 0.5.

With the retained fraction at 0.1% instead of 1%, the outcomes are the same. At 10%, 13 converge, 4 fail with `JACOBIAN_75_TIMES_BAD` and 7 reach the iteration limit.

On the test boundary, main's own converged state moves steadily with the time step. The move is in the m = 1, n = 1 harmonic of Z, and tightening `ftol` from 1e-9 to 1e-15 leaves it unchanged. === PR #500 [CLOSED, not merged] Replace dense DFT toroidal loops with FFT c2r/r2c transforms ===

--- description by Copilot, 2026-04-28 07:47 UTC ---
VMEC++ uses `O(nZeta × ntor)` dense dot-product loops for the toroidal direction in its two core transforms.
Since the toroidal grid is uniform, these are exact DFTs and can be replaced with FFTs, reducing complexity to `O(nZeta × log(nZeta))`.

For stellarator symmetric boundaries, the DFTs are actually either only involving `sin` or only `cos` terms (DST, DCT). Combined with the low resolutions typically used in VMEC, this means a naive FFT is typically slower than a well optimized DST or DCT.

The key insight on how to still utilize FFT came from @VisionAndMind https://github.com/VisionAndMind , who pointed out that the DST and DCT could be interleaved into a single mixed FFT and dealiased afterwards.

=== PR #510 [CLOSED, not merged, draft] Replace OMP critical reductions with atomic adds ===

--- description by jurasic-pf, 2026-05-04 18:26 UTC ---
Replace OMP critical reductions with atomic adds

The hot iteration in IdealMhdModel::update() performed several reductions
via `#pragma omp critical { x += local; }` patterns: force residuals
(fResInvar, fResPrecd), energies (thermalEnergy, magneticEnergy), force
norms (fNormRZ, fNormL, fNorm1), volumes (voli, plasmaVolume), the bad-
Jacobian flag, and the spectral-width accumulators. Each critical
serialised every thread on a single team-wide lock, even when the
contributions touched independent array elements.

Replace each with `#pragma omp atomic` (or `atomic write` for the enum
flag) so threads can interleave per-element updates. Numerics are
preserved within the existing OpenMP non-determinism noise floor.

Modest measured speedup at 4-8 threads on examples/data/w7x.json
(+3-4%). The remaining act-vs-passive gap is dominated by barrier
wake-up cost rather than critical-section contention; that will be
addressed in follow-up work.

Add OMP barrier scaling benchmark script

scripts/bench_omp_barriers.py runs vmecpp -t {1,2,4,8} under both
OMP_WAIT_POLICY=active and =passive (3 repeats each), reporting
wall-clock medians, the active/passive ratio, and parallel scaling
efficiency. Optional --venv2 flag does the same sweep for a second
build and prints a side-by-side comparison.

Important: the script pins OPENBLAS_NUM_THREADS=1 and
MKL_NUM_THREADS=1. Without these, numpy and scipy each spawn their
own BLAS thread pool sized to nproc, which on a 4-thread vmecpp run
caused ~27% of CPU time to go to blas_thread_server (oversubscription
between OMP and BLAS pools). Pinning BLAS to one thread cleans up
the OMP timings.

evalFResInvar and evalFResPrecd previously used a three-rendezvous
synchronisation pattern around each call:

[code omitted]

Replace with a one-rendezvous pattern using per-thread slots in
HandoverStorage:

[code omitted]

The slot writes touch each thread's own row, so they cannot conflict.
After the barrier, each thread independently sums the columns into a
private stack-frame copy of `total` and the designated thread publishes
the totals and the derived residual norms to flow control. The
nowait-publish is safe because every consumer of fsqr/fsqz/fsql or

(assembleTotalForces, the convergence-check single in vmec.cc, etc.).

The wins are exactly where the theory predicts: removed rendezvous
under OMP_WAIT_POLICY=passive avoid futex-sleep round-trips that
dominate that mode's overhead. Active policy is unaffected because
threads spin instead of sleep. The pattern compounds with thread
count and is more visible on heavier inputs.

Bench script updated to 7 repeats per (threads, policy) pair for a
tighter confidence interval on the median.

Per-thread slot reduction for energies and spectral width

Apply the same per-thread slot pattern to the two remaining hot-path
reductions in IdealMhdModel::update() / Vmec::Printout:

* `pressureAndEnergies` -- aggregates `thermalEnergy` and
  `magneticEnergy` and derives `mhdEnergy`. The previous
  `single{reset} / atomic+ / barrier / single{finalize} / barrier`
  pattern collapses to `slot[tid] = local / barrier / colwise.sum /
  single nowait{publish}` (one rendezvous instead of three).

* The volume-averaged spectral-width accumulator. The two scalar
  fields `spectral_width_numerator_` / `_denominator_` are removed;
  `RegisterSpectralWidthContribution` now writes into a per-thread
  row of `spectral_width_slots_` and `VolumeAveragedSpectralWidth`
  computes the column sum on demand. The old reset-single in
  `Vmec::Printout` is dropped: each iteration's writes overwrite the

within the OMP non-determinism floor (max rel 1e-5 on rmnc/zmns/lmns,
1e-12 on iotaf, 1e-14 on energies). Wall-time gain on this short
input is below the bench's noise floor (~3 %); the change brings
every reduction in the hot path onto the uniform slot pattern, which
keeps the codebase easier to reason about and removes the last of
the `single{reset}/atomic/barrier/single{finalize}` boilerplate.

## Motivation

#315 asks to "only consider non-zero Fourier coefficients in the computation," to cheaply explore high-frequency perturbations to an equilibrium and global perturbations whose toroidal mode numbers are not multiples of NFP.

Today the mode set is the dense grid: poloidal `m` in `[0, mpol)`, toroidal `n` in `[-ntor, ntor]`, with the toroidal basis hard-wired to `n*nfp`. Adding a single high-`m` mode, or a non-axisymmetric mode at `nfp=1`, forces the full dense grid and pays for every intermediate mode even though it stays at (or near) zero.

This adds an opt-in sparse mode set: the geometry (and, with `sparse_lambda`, lambda) is restricted to an explicit set of free modes, and the Fourier transforms iterate only those modes. A reduced-resolution base equilibrium can then carry a few explicit high-frequency or global modes, computed at a fraction of the dense cost, while everything else is frozen at zero.

## Approach

Two inputs build on the geometry masking from #598 (`mpol_geometry`/`ntor_geometry` freeze R/Z above a cap):

- `extra_geometry_m` / `extra_geometry_n`: an explicit list of `(m, n)` geometry modes kept free *above* the cap. The active geometry set is the cap rectangle plus these extras; everything else is frozen at zero each iteration (force and state), so a single perturbation mode can be added to a converged base and studied in isolation.
- `sparse_lambda`: also restricts lambda to the active set, which lets the transforms skip the frozen modes. The frozen modes are exactly zero, so skipping their work is identical to the dense transform:
  - whole poloidal rows with no free mode are skipped in the inverse and forward DFTs (2D and 3D);
  - the toroidal sums run only up to the highest free `n` at each `m`.

  The preconditioner still masks the frozen modes to zero (correct, computed-then-discarded); skipping its per-mode solve as well is left out because a frozen mode's force is already zero, so it contributes nothing.

Global, non-NFP perturbations are reached by running `nfp=1` (the full torus, where every integer `n` is a valid toroidal mode) with a sparse mode set, so the cost of the otherwise-dense high-`ntor` grid is avoided.

When neither input is set (the default), nothing is masked and the transforms run the dense path unchanged.

## Changes

- `vmec_indata`: `extra_geometry_m` / `extra_geometry_n` and `sparse_lambda` inputs, with JSON and HDF5 read/write and an `extra_geometry_*` length-consistency check.
- `sizes`: derive the active-mode mask and `isActiveGeometryMode` / `anyActiveGeometryAtM` / `maxActiveGeometryNAtM` helpers.
- `fourier_coefficients`: `maskGeometryAbove` keeps the extra modes and, under `sparse_lambda`, also freezes lambda.
- `dft_toroidal` / `ideal_mhd_model`: the inverse and forward symmetric DFTs (2D and 3D) skip frozen poloidal rows and shorten the toroidal sums under `sparse_lambda`.
- `pybind_vmec.cc` / `__init__.py`: expose the three inputs.

## Validation

Skipping the frozen modes is bit-identical to the dense (masked) transform: on solovev with a geometry cap and a kept `m=4` extra, the converged MHD energy is `2.546537` with and without the poloidal-row skip; on an `nfp=1` run with a global `(m=1, n=1)` mode it is `2.549049` with and without the toroidal-sum shortening.

Cost, single grid `ns=51`, `mpol=60`, 600 iterations: the dense run takes `0.75 s`; the same base with the geometry capped at `m<3` and `sparse_lambda` takes `0.49 s` (the transform no longer touches the 57 frozen rows; the remaining cost is the real-space physics on the grid, which a high mode still requires).

The non-NFP capability runs end to end: a global `n=1` mode on an axisymmetric base at `nfp=1`, kept as a sparse extra, converges to `ftol = 1e-11` in 197 iterations.

Default (no extras, `sparse_lambda=False`) is a no-op: the #598 `test_lambda_resolution.py` cases, including the cap-at-full-resolution array-for-array equality, are unchanged.

## Test

`tests/test_extra_geometry_modes.py`:
- `test_extra_mode_kept_above_geometry_cap` / `test_only_listed_extra_modes_are_kept`: a high-`m` perturbation is frozen to zero under the cap, kept (matching the full-resolution run) when listed as an extra mode, and only the listed modes are kept;
- `test_sparse_lambda_freezes_lambda_above_cap`: `sparse_lambda` freezes lambda above the cap to exactly zero, where it otherwise carries content;
- `test_non_nfp_global_perturbation_runs_sparsely`: an `nfp=1` global `(m=1, n=1)` mode is kept while the frozen `n=2` modes stay at zero.

=== PR #616 [CLOSED, not merged] 2D block-tridiagonal preconditioner ===

--- description by CharlesCNorton, 2026-07-08 20:52 UTC ---
VMEC++'s convergence preconditioner is the per-mode radial operator assembled in `computePreconditioningMatrix` and applied in `applyRZPreconditioner`: for each Fourier mode `(m, n)` it solves a scalar tridiagonal system down the radial grid, the poloidal and toroidal mode numbers entering only as diagonal `m²` and `(n·nfp)²` weights. Different modes are never coupled to one another. That approximation is cheap and robust, but it is also the one that weakens on strongly-shaped, high-mode-number equilibria, where the true Hessian couples the poloidal modes within a flux surface. PARVMEC handles this with `precon2d`/BCYCLIC: a dense per-surface block coupling all poloidal modes, with the surfaces tied together radially into a block-tridiagonal system. This PR lands the block-tridiagonal solver and the wiring that reshapes the R/Z preconditioner into that form; the mode-coupling coefficients that make it a genuine 2D preconditioner follow on this branch.

## What

**`common/block_tridiagonal`** — a standalone, dependency-light package:

- `BlockTridiagonalFactorization` — block-Thomas factorization and solve for `L_j x_{j-1} + D_j x_j + U_j x_{j+1} = b_j` over `n` block rows of size `k`. The forward sweep stores the explicit inverse of each reduced pivot block, so the many right-hand sides that share one operator (one per Fourier basis function) reuse a single factorization.
- `AssembleFdBlockTridiagonal` — assembles the Jacobian `dF/dx` of a force field with nearest-neighbour radial coupling by central finite differences. Perturbing surface `j` moves the force only on surfaces `j-1, j, j+1`, so surfaces three apart are perturbed together and the assembly costs `6·k` force evaluations independent of the number of surfaces.
- Unit tests for both, checked against a known analytic solution, a dense `(n·k)×(n·k)` reference solve, and an analytic Jacobian, across a range of block counts and block sizes.

**`applyRZPreconditioner`** — an opt-in path, `solveBlockRZPreconditioner`, that regroups the R/Z preconditioner as one block-tridiagonal system per toroidal mode number `n`: the poloidal modes of a surface form each block, the radial grid indexes the block rows, and the system is solved with the new factorization. It is gated behind `VMECPP_PREC2D`; the per-mode scalar solve remains the default and is untouched.

## Verification

- With only the block diagonals populated from the existing 1D coefficients, the block operator is algebraically the per-mode scalar solve, so the two converge to the same equilibrium up to floating-point round-off. On `cth_like_fixed_bdy` and `solovev`, converged `volume_p` and `aspect` match the default to all printed digits and `betatotal` and the magnetic-axis position agree to `~1e-12`, with `VMECPP_PREC2D` set and unset; the residual difference is the block-Thomas sweep's arithmetic ordering.
- `BlockTridiagonalFactorization` matches both the analytic solution and the dense reference solve to machine precision (`~1e-14`); `AssembleFdBlockTridiagonal` recovers the analytic Jacobian of a known nearest-neighbour force field.
- Full CMake build; Bazel targets and deps added for the new package. clang-format and clang-tidy clean.

## Follow-up

The off-diagonal poloidal coupling is the angle-resolved form of the same metric integrals that `computePreconditioningMatrix` currently angle-averages into the per-mode diagonal (`ax`/`bx` summed over the poloidal grid). Adding those harmonics to the block off-diagonals, together with the second-order solve that consumes them, turns this into the full 2D preconditioner and lands next on this branch.

=== PR #629 [CLOSED, not merged] Free boundary (#628): convergence diagnosis, edge preconditioner, and AEGIS virtual-casing solver ===

--- description by CharlesCNorton, 2026-07-10 02:10 UTC ---
Toward #628: a robust and accurate free-boundary solver. This addresses both halves the issue names, the convergence dynamics of the exterior-field coupling and the accuracy of the exterior-field solver itself, and adds AEGIS, a virtual-casing exterior-field solver.

## The convergence dynamics

The free-boundary iteration slows with poloidal resolution while the fixed-boundary iteration saturates:

| mpol | fixed | free (ftol 1e-10) |
|---|---|---|
| 5 | 416 | 490 |
| 12 | 561 | 1606 |
| 16 | 566 | 2094 |
| 20 | 565 | 2579 |

The first read of this coupling inferred a near-singular edge-force block from a finite-difference Jacobian: an exact (ntor+1)-dimensional null space over the vertical Z(m=0, all n) modes (which VMEC stabilizes only at Z(0,0)) plus a continuum of weakly-restored high-m edge modes. Driving the low-level `VmecModel` from Python (the merged `hessian_vector_product` / `solve_equilibrium` machinery, #580) lets that operator be measured directly rather than inferred, and the direct measurement revises the picture:

- **The LCFS edge-force Jacobian is well-conditioned, not singular.** Building `dF_edge/dx_edge` by finite differences at a converged surface gives 207 active modes (of 240; the rest are structural-zero Fourier entries, which accounts for most of the "null space" the FD Hessian reported) with condition number `6.4e3` and a smooth singular spectrum (513 down to 0.08), no near-null cluster.
- **The obstacle is the coupling, not any single block.** An edge-only Newton step reduces the edge force 21x but raises the *total* residual: moving the boundary disturbs the interior more than it settles the edge. Edge and interior are strongly, non-separably coupled, through the vacuum pressure (a global boundary integral) and through the radial metric.
- **The full coupled force Jacobian has a broad near-null continuum.** Its singular spectrum is ~1061 structural zeros plus a continuum of small singular values (physical condition number ~1e8). Native momentum converges because its preconditioned monotonic damping crushes every mode, slowly; the runaway is momentum's `~sqrt(cond)*log(1/tol)` scaling, dominated by the edge continuum that VMEC's per-mode preconditioner cannot couple.

This is why inversion- and extrapolation-based accelerators, built on the finite-difference operator, do not beat momentum here, refining the earlier "inversion-based preconditioners do not help" into a mechanism: the small singular values sit at or below the FD/NESTOR noise floor (~1e-4 relative at the best step size; the default HVP step `eps_rel=1e-7` is already in the noisy regime). A matrix-free Newton-Krylov solve preconditioned by `M^-1` stalls (GMRES linear residual 0.13-0.98 after 300 matvecs); an SVD-truncated Hessian inverse and a full finite-difference block-tridiagonal preconditioner do not produce a descent direction once the interior/lambda coupling is dropped; Anderson acceleration plateaus (extrapolating a lambda-dominated preconditioned residual); a scalar edge boost (VMEC's commented-out `ledge`) destabilises on the directional stiffness. The native momentum iteration converges (slowly) precisely because it does not invert the operator, and a mode-diagonal preconditioner cannot represent the coupled edge block. Robust tight-tolerance acceleration needs a *noise-free* operator (see "What remains"). This is the "poor convergence dynamics that must be understood first" the issue names.

## The edge preconditioner (opt-in)

`assembleRZPreconditioner` gains an opt-in m-dependent edge damping (`VMECPP_EDGE_A`, `VMECPP_EDGE_P`), default off and byte-identical to the previous flat pedestal. With it on, the loose-to-moderate-tolerance free-boundary iteration collapses onto the fixed-boundary floor (cth_like mpol 16: 2094 to 581 at ftol 1e-10, flat across resolution, equilibrium invariant to 1e-5). It does not resolve tight-tolerance convergence: a scalar/diagonal edge damping cannot represent the dense, directional edge-interior coupling the measurements above show, so the final residual reduction stalls. It is kept default off as a loose-tolerance accelerator while the proper coupled edge preconditioning is developed, for which the block-tridiagonal infrastructure in #616 is the vehicle.

## The vacuum-coupling lag is a first-order control

The free-boundary iteration is a Picard iteration on the vacuum coupling, with the NESTOR-recompute cadence `nvacskip` setting the lag. Fresh vacuum (`nvacskip=1`) cuts the iteration count and, crucially, flattens the runaway (cth_like, robust style, ftol 1e-11):

| mpol | nvacskip=9 (default) | nvacskip=1 |
|---|---|---|
| 5 | 600 | 497 |
| 12 | 2386 | 1151 |
| 16 | 3781 | 1526 |
| 20 | 4888 | 1991 |

The benefit grows with resolution (1.2x at mpol 5, 2.5x at mpol 16-20): the iteration-count runaway is roughly halved in slope. The trade is per-iteration NESTOR cost. The point is that the coupling dynamics are directly controllable, and that fresher coupling matters more as the equilibrium is more strongly shaped, which is exactly where a stiffer, more accurate exterior solver is coupled.

## AEGIS: the accurate exterior-field solver

`examples/aegis_virtual_casing.py` is a validated virtual-casing exterior-field solver, a higher-order alternative to NESTOR's scalar-potential vacuum field. AEGIS (Accurate Exterior Green's Integral Solver) computes the exterior field on the LCFS from the virtual-casing principle: the plasma's exterior field is the Biot-Savart field of the equivalent surface current K = n x B_plasma (plus the n.B_plasma monopole term), with the near-singular self-interaction resolved by Quadrature By Expansion (QBX). Unlike NESTOR, which LU-solves a dense boundary-integral system for a scalar potential every ivacskip iterations, AEGIS evaluates the Green's integral directly from the known surface current, with no linear solve.

Validated on cth_like:

- Biot-Savart integrator vs an analytic current loop: relative error 1e-14.
- LCFS geometry and field reconstruction: B.n/|B| = 2e-16 (tangent to the flux surface).
- Jump condition n x (B_out - B_in) = K via QBX: mean 1%, max 4% across the surface.
- Free-boundary physics: the exterior field B_coil + VC(n x B_plasma) is tangent to the LCFS, and its magnitude equals the interior field at a converged equilibrium (|B_ext|/|B_in| = 0.985).
- End to end, on the same cth_like equilibrium, AEGIS and NESTOR agree on the LCFS vacuum-pressure distribution to 2.8% (mean 0.173 vs 0.178, and standard deviation, min, and max all within 3%): two independent methods, the same exterior field.

A C++ module `free_boundary/aegis/` lands the numerical core: `VirtualCasing` (Biot-Savart + QBX, matching the Python reference to four digits, with a self-contained magnetized-sphere gtest to <0.1%) and the `VacuumPressure` solver entry point that returns |B_exterior|^2/2 per LCFS point.

AEGIS is also wired into the free-boundary iteration itself (opt-in via `VMECPP_AEGIS`): `computeAegisVacuumPressure` reuses NESTOR's LCFS surface geometry and coil field (`GetSurfaceGeometry`/`GetExternalMagneticField`) and the interior equilibrium field (`bsupu`/`bsupv` extrapolated to the LCFS), replicates the field period, and overwrites `vacuum_magnetic_pressure` in place. Live on cth_like it reproduces NESTOR's per-point pressure to under 4%, confirming the geometry, coil field, interior-field, and field-period handling end to end.

## What remains

The convergence work above says the tight-tolerance accelerator must be built on a *noise-free* coupled operator, and the near-singular edge coupling was the obstacle to inversion only in the sense that the FD operator's small singular values were unrecoverable from noise. The exterior-field coupling makes the noise-free path concrete, and each ingredient exists in the tree:

- **Analytic vacuum Jacobian.** `dP_vac/dgeometry` is available in closed form: the chain is `geometry -> amat/bvec (NESTOR) -> potential -> bSubU,bSubV -> P_vac`, and `damat/dgeometry` is exactly the Green's-function derivative `grpmn` that `SingularIntegrals`/`LaplaceSolver` already compute each solve. This gives the dense edge coupling with no finite-difference noise.
- **Exact MHD Hessian.** The Enzyme autodiff force Hessian (#573/#582) supplies the interior/lambda blocks noise-free, removing the FD floor that caps the Newton-Krylov path here.
- **2D block-tridiagonal preconditioner.** #616 lands the block-tridiagonal solver and the radial wiring; populating the LCFS block from the analytic vacuum Jacobian and the interior blocks from the metric integrals turns it into the coupled preconditioner the measurements call for, and which a stiffer, more accurate exterior field makes only more necessary.
- **Accelerating the Picard coupling directly** (Anderson / Chebyshev on the vacuum-pressure sequence; a frozen-vacuum inner Newton with an outer vacuum Picard), and reducing the per-iteration cost of the virtual-casing evaluation (the QBX self-interaction is the dominant term) so a fresh-vacuum coupling is cheap.

--- comment by CharlesCNorton, 2026-07-11 03:04 UTC ---
**Physical surface current: it tracks the boundary pressure jump, not the virtual casing.**

The physical tangential-field jump `n x (B_out - B_in)` at the LCFS is distinct from the virtual-casing current `K = n x B_plasma`, which is nonzero at every point by construction. On these free-boundary cases the edge total-pressure jump vanishes, so the physical surface current must too, and it does: it sits at the on-surface quadrature floor (~1.7e-3 relative) with no sheet current. Imposing a nonzero edge pressure (a uniform pedestal on the Solovev mass profile, `p(edge) = pres_scale * d`) raises it, so a physical current appears only when there is a pressure jump.

Its quantitative scaling on the axisymmetric case is not cleanly separable from that floor, because the pressure-driven magnitude excess `|B_out|^2 - |B_in|^2 = 2 mu0 p(edge)` is absorbed into AEGIS's residual normal-field error `n.B_ext` rather than the tangential jump. That floor is not a limitation of the singularity-subtracted quadrature itself. On a balanced (isotropic) source grid AEGIS's `n.B_ext` converges to BIEST's high-order value (~1.5e-4, matched to a factor of order one); the coupling's higher floor is the aspect ratio of its axisymmetric source grid (poloidal `nThetaEff ~ 16` against the toroidal upsampling to 256). Rebalancing the toroidal count recovers ~20% of both the surface-current floor and delbsq. The effect is confined to `ntor = 0`, where NESTOR's few-mode solve is already near-exact; the three-dimensional grid is balanced and unaffected.

Reproducible scripts under `examples/aegis_verification/`: `surface_current.py` (current versus edge pressure), `floor_diag.py` (the floor is the poloidal quadrature, falling with mpol and flat with ns), `onsurface_accuracy.py` (AEGIS versus BIEST on a balanced grid), `ntor_aspect.py` (the aspect-ratio dependence).

**Status, validated against BIEST as the golden reference (per the recommendation above).**

**What we found.** On both cth_like and a 3D high-beta NCSX free-boundary case, AEGIS's *coupled* equilibrium reaches a lower `delbsq` than NESTOR but a **less self-consistent boundary**: the golden BIEST field pierces the AEGIS boundary at `n.B/|B|` ~ 1-2% (NESTOR ~ 0.2%), with an over-shifted magnetic axis. So the wall is the vacuum-field *magnitude* accuracy, not the tangency, and it is not resolution-limited (flat across mpol 6-14).

**What remains.** The accurate *and* tangent coupling already exists as BIEST's own `ExtVacuumField::ComputeBplasma`: it solves exactly this exterior Neumann BVP - `grad S[sigma] + curl S[J]` with the total field tangent on the surface - using high-order singular quadrature via GMRES. The native parvmec iteration style (#612) ported PARVMEC's time-step control criteria (dual res0/res1 residual minima, 1e4 leash, gentle non-escalating revert) but kept VMEC 8.52's placement and bookkeeping. PARVMEC's TimeStepControl differs structurally (evolve.f, eqsolve.f):

- it runs BETWEEN the force evaluation and the descent step, so it stores the pre-step state whose residuals were just measured, never a post-step state with unknown residuals (ORNL moved it there "TO AVOID STORING A POSSIBLE irst=2 STATE");
- its store/leash decisions compare the PREVIOUS iteration's preconditioned residual sum (fsq is only updated to fsq1 after the control) together with the current invariant residuals;
- a revert sets iter1 = iter2 and immediately re-evaluates the MHD forces at the restored state, then still takes a descent step in the same iteration;
- iter2 keeps advancing on revert iterations (no VMEC 8.52 "cycle"), so res0/res1 stay true running minima of the whole multigrid stage -- the 8.52-style iter2 freeze made vmecpp re-enter with iter2 == iter1 and RESET both minima after every revert -- and the NESTOR vacuum update cadence ivacskip = (iter2 - iter1) % nvacskip is preserved;
- the store is guarded by irst == 1, and the ijacob 25/50 escalation does not reset delt0r to 0.98/0.96 * delt (PARVMEC commented that reset out: "!changed in restart").

Implement PARVMEC's control literally in Vmec::ParvmecTimeStepControl, called from Evolve between the convergence check and the descent step, and bypass the post-step 8.52 control and iter2 freeze for this style. The Python iteration driver gets the identical restructure so the native and Python parvmec loops keep matching step for step. The default vmec_8_52 path is byte-for-byte unchanged.

Extend the PARVMEC reference test with the free-boundary cth_like case: free boundary is where the ported control diverged from PARVMEC (the pre-step control interleaves with the NESTOR update cadence and a revert re-evaluates the vacuum contribution), and it was previously only validated on fixed-boundary cases. The committed reference wout was cross-checked against a fresh ORNL-Fusion/PARVMEC free-boundary run of the same input (agreement at the ~4e-4 inter-implementation NESTOR floor); VMEC++'s parvmec style reproduces the reference to ~1e-13.

=== PR #730 [CLOSED, not merged] Assemble the axis-guess boundary geometry over the full poloidal interval ===

--- description by CharlesCNorton, 2026-08-31 17:22 UTC ---
Stacked on #729; the first commit is that one.

`RecomputeMagneticAxisToFixJacobianSign` evaluates the boundary against `FourierBasisFastPoloidal`, which tabulates the poloidal basis on `[0, pi]` only, and reconstructs the rest of the interval by mirroring. The mirror sits inside `if (!s.lasym)`, so without stellarator symmetry the extended interval keeps the zeros from `resize`. `min_element` over `r_lcfs[k]` then gives 0 rather than the inboard extent, and the minimum of `tau` over the poloidal index picks up the same zeros, so `min_tau_temp > min_tau` never holds and the search returns the grid centre in every plane. The reconstruction now follows `symrzl`: the antisymmetric part is accumulated apart from the symmetric one, the extended interval is formed from both before the antisymmetric part is added into the reduced one, with R and dZ/dTheta even under `(theta, zeta) -> (-theta, -zeta)` and Z and dR/dTheta odd. Under stellarator symmetry the antisymmetric part is zero and this is the previous mirror. Every plane is searched when there is no symmetry to mirror across, and the half-period plane counts as its own mirror only when a grid point falls on it, which an odd `nZeta` has not.

Three tests. The assembled geometry is compared against a direct evaluation of the Fourier series over the full poloidal interval, on the bundled cases and on a boundary given antisymmetric content in both R and Z. A stellarator-symmetric boundary driven through the `lasym` path reaches the same axis as through the symmetric one.

--- description by CharlesCNorton, 2026-09-01 21:40 UTC ---
`BoozerTransform` (C++, `vmecpp/vmec/boozer`) and `vmecpp.boozer_transform` (Python) compute the Boozer coordinates of the half-grid flux surfaces of a converged stellarator-symmetric equilibrium from its `wout`: the Boozer spectra of |B|, R, Z, the angle transformation function nu and the Boozer Jacobian, together with G, I and iota per surface and the mode numbers in the `wout` convention.

The Boozer angles are theta_B = theta + lambda + iota nu and zeta_B = zeta + nu, with nu = (w - I lambda) / (G + iota I) and w the periodic part of the magnetic scalar potential on the surface, assembled mode by mode from B_theta and B_zeta. Each spectrum is a direct quadrature over the VMEC angles carrying the Jacobian of the angle map, so the map is never inverted. Geometry is taken to the half grid as booz_xform does, odd-m coefficients interpolated as coefficient / sqrt(s) with the m = 1 quotient extrapolated to the axis on the first half-grid surface, and the Jacobian is reported as (G + iota I) / |B|^2 in the Boozer angles. `jacobian_spread` gives per surface the relative variation of sqrt(g_B) |B|^2, which is a flux function in exact Boozer coordinates and so measures the residual of the transformation.

Verification is `tests/test_boozer.py` and `vmecpp/vmec/boozer:boozer_test`. On `cth_like_fixed_bdy` with mboz = nboz = 8 every surface and mode of `bmnc_b`, `rmnc_b`, `zmns_b`, `numns_b` and `gmnc_b` agrees with booz_xform 0.1.0 to 1e-9 of the largest coefficient of the array (the test is skipped when booz_xform is not installed), and G and I agree with `bvco` and `buco` exactly. The C++ tests check that sqrt(g_B) |B|^2 is a flux function to the force tolerance of the case, that the Jacobian-weighted surface average of |B| is the same in the VMEC and Boozer angles, that an axisymmetric equilibrium has no toroidal Boozer harmonics, and the argument validation. Non-stellarator-symmetric equilibria return `Unimplemented`.

=== PR #876 [CLOSED, not merged] Close the bootstrap current inside the solve ===

## Change

`bootstrap_current = true` replaces the enclosed toroidal current profile by the bootstrap current of the Redl closure during the iteration. Every 25 iterations, once the force residuals are below 1e-2, each thread evaluates the closure on its half surfaces from `bsupu`, `bsubu`, `bsupv`, `bsubv` and `gsqrt`: trapped fraction, `B_max`, `B_min`, `<B^2>`, `<1/B>`, and `<J.B>` with `G = bvcoH`, `I = bucoH`, `iota = chipH / phipH` and `psi_edge = -phi_edge / (2 pi)`. One thread integrates `(I/G)' = signgs mu0 <J.B> dVds / G^2` from the axis and writes the relaxed profile `currH + 0.5 (I_bs - currH)` back. `computeBContra` turns it into `chi'` at the next iteration. The run is converged when the force residuals are below `ftol` and the change in iota the closure last asked for, `max_j |I_bs - currH| / (|phip| <guu / sqrt(g)>)`, is below `bootstrap_tolerance` (default 1e-3). The profile carries across multigrid steps by linear interpolation.

`bootstrap_ne`, `bootstrap_te` and `bootstrap_ti` are power series in the normalized toroidal flux in 1e20 m^-3 and keV. With `ncurr = 1` the enclosed current is an input, so an equilibrium answers for a current the plasma may not carry. A stellarator at steady state carries the current its own density and temperature gradients drive. An outer loop around the solver costs a solve per iteration and breaks the derivative chain.
